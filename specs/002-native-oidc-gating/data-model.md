# Data Model: Native OIDC Gating

Phase 1 output for [plan.md](plan.md).

## Inventory fields (hosts, guests, external sites)

Added to `HostEntrySchema`, `GuestEntrySchema` and `ExternalSiteSchema` in `src/lib/inventory.ts`,
next to `authGroup` and `unauthenticatedPaths`.

| Field | Type | Column | Notes |
|---|---|---|---|
| `authMode` | `'forward' \| 'oidc'`, optional | `auth_mode TEXT` | Absent means `forward`. Only meaningful with `authGroup`. |
| `oidcRedirectUris` | `string[]`, optional | `oidc_redirect_uris_json TEXT` | Each an absolute `http://` or `https://` URL. Deduplicated, order kept. |

Both columns are added to existing databases with the existing `ensureColumn` helper, so no
migration step and no forward-only break: an older build ignores the new columns.
`saveInventory`/`loadInventory` round-trip them like `unauthenticated_paths_json`.

### Derived state

`effectiveAuth(entry)` (new, `src/lib/inventory.ts`):

| `authGroup` | `authMode` | Result |
|---|---|---|
| unset | any | `ungated` |
| set | unset or `forward` | `forward` |
| set | `oidc` | `oidc` |

Every consumer (`buildCaddyBlock`, `runSyncAuthentik`, the edit confirmation rule, the web UI)
uses this one function, so they cannot disagree about whether an entry is OIDC-gated.

### Validation

- Schema level (every load): enum and URL format only.
- Write level (`parseAuthMode`, `parseOidcRedirectUris`, and `oidcConfigErrors(entry)` called from
  `commitGuestEdit`): an entry whose `effectiveAuth` is `oidc` and has subdomains must have at least
  one redirect URI. Error text names the field (`oidcRedirectUris` / "Callback URLs").
- `validateInventory()`: only change is narrowing the `authentik: true` requirement to
  forward-auth-gated entries (research R10).

### Edit transitions and permissions

| Change | Who | Confirmation |
|---|---|---|
| Set or change `authMode` | admin | Needed when it takes an `oidc`-effective entry to `forward` |
| Set or change `oidcRedirectUris` | admin | None |
| Clear `authGroup` on an `oidc`-effective entry | admin (existing rule) | Needed |
| Raise `authGroup` on an `oidc`-effective entry | anyone with resource access (existing rule) | None |

## Authentik objects (not stored by Bellhop)

### OpenID client (Authentik OAuth2 provider)

| Attribute | Value set by the sync |
|---|---|
| `name` | entry slug (`subdomains[0]`) |
| `client_type` | `confidential` |
| `grant_types` | `authorization_code`, `refresh_token` |
| `signing_key` | key named by `AUTHENTIK_OIDC_SIGNING_KEY_NAME` |
| `property_mappings` | managed scope mappings for `openid`, `profile`, `email` |
| `redirect_uris` | one `{ matching_mode: strict, url }` per `oidcRedirectUris` entry |
| `authorization_flow`, `invalidation_flow` | existing `authentikConfig()` flow slugs |
| `client_id`, `client_secret` | generated by Authentik on create, never sent afterward |

### Application

Unchanged from forward-auth except: `provider` points at the OpenID client, and
`meta_publisher = "bellhop"` marks it as owned (research R1).

### Ownership states for an inventory slug

| Application at slug | Provider kind | `meta_publisher` | Sync treats it as |
|---|---|---|---|
| none | — | — | free: create |
| exists | proxy | any | owned (unchanged #154 rule) |
| exists | OAuth2 | `bellhop` | owned |
| exists | OAuth2 | anything else | conflict, adoptable |
| exists | other or none | — | conflict, not adoptable |

## Sync result additions (`SyncAuthentikResult`)

| Field | Type | Meaning |
|---|---|---|
| `oidcToCreate` | `string[]` | Slugs getting a new OpenID client (and Application) |
| `oidcUpdates` | `{ slug, changes: string[] }[]` | Settings drift fixed in place; `changes` names each field |
| `modeSwitches` | `{ slug, from: 'forward' \| 'oidc', to }[]` | Provider swaps (research R5) |
| `oidcDeletions` | `string[]` | Slugs whose OpenID client is deleted (mode switch or gate cleared); drives the dry-run warning |
| `oidcSkipped` | `{ slug, reason }[]` | Missing callback URL, missing signing key, missing scope mapping |
| `discovery` | `{ slug, issuer, ok, error? }[]` | Apply only; the post-apply discovery check |

`toCreate` keeps meaning new forward-auth Applications, so existing callers and tests are
unaffected. `toRemove` covers every owned Application being deleted, of either kind; an OIDC one
also appears in `oidcDeletions`. `conflicts` gains OIDC-mode entries blocked by an unowned
Application.
