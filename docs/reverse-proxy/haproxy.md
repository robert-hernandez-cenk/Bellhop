# HAProxy driver

Select it with `bellhop set-config proxyDriver haproxy --apply` (or the
Settings page, where it's the "HAProxy" option). Everything the drivers
share (how a driver is chosen, capability checks, the dry run) is described
in [Reverse proxy drivers](README.md). The driver's output was checked with
a real `haproxy -c` against HAProxy 2.6 (the Debian bookworm package's
branch) and 3.4.

Unlike the Caddy and nginx drivers, it doesn't own the part of the
configuration that listens for traffic. Your own `haproxy.cfg` keeps the
`frontend` — the `:443` bind, its certificates, its default backend and
anything else it already serves — and Bellhop owns only the backends that
frontend routes to, plus a map from hostname to backend.

## The two files

`sync-proxy` writes two files on the proxy host, both replaced whole on
every apply:

- **The backends file**, at `proxyConfigPath` (default
  `/etc/haproxy/bellhop.cfg`): one `backend` block per subdomain-bearing
  inventory entry.
- **The map file**, `bellhop.map` in the same directory as the backends
  file (so `/etc/haproxy/bellhop.map` by default): one
  `<hostname> <backend>` line per subdomain, lower-cased, each entry's
  canonical subdomain first. It always sits beside the backends file —
  moving `proxyConfigPath` moves both — so `proxyConfigPath` itself can't
  be named `bellhop.map`.

For a guest `web-lxc` at `192.0.2.10:8080` with subdomains `web` and `www`,
and a domain of `example.com`, the backends file holds:

```haproxy
# Generated by Bellhop sync-proxy for HAProxy. Do not edit: this file is replaced on every apply.

backend bellhop_guest_web-lxc
    mode http
    timeout server 1d
    timeout tunnel 1d
    http-request del-header x-authentik- -m beg
    http-request set-header X-Forwarded-For %[src]
    http-request set-header X-Forwarded-Proto https
    http-request set-header X-Forwarded-Host %[req.hdr(host)]
    http-request set-header X-Forwarded-Port 443
    server app 192.0.2.10:8080
```

and the map file:

```text
# Generated by Bellhop sync-proxy for HAProxy. Do not edit: this file is replaced on every apply.
web.example.com bellhop_guest_web-lxc
www.example.com bellhop_guest_web-lxc
```

Backend names are `bellhop_<type>_<name>`, where the type is `host`,
`guest` or `externalSite`, so a host and a guest sharing a name never
collide, and the `bellhop_` prefix keeps them clear of your own backends.
Any character HAProxy doesn't allow in a backend name (anything other than
letters, digits, `-`, `_`, `.` and `:`) becomes `_`; if two entries end up
with the same name that way, the later one gets `_2`, `_3`, and so on.

With no subdomain-bearing entries at all, both files are just the header
line, which HAProxy accepts.

## Prerequisites

Three things are yours to set up once, before the first apply.

**Load the backends file.** HAProxy only reads the files it's given with
`-f`. On Debian/Ubuntu, add this to `/etc/default/haproxy`, which the
packaged systemd unit appends to its command line:

```sh
EXTRAOPTS="-S /run/haproxy-master.sock -f /etc/haproxy/bellhop.cfg"
```

The unit already sets `EXTRAOPTS=-S /run/haproxy-master.sock` (its master
socket) by default, and a value in `/etc/default/haproxy` replaces that
rather than adding to it, so repeat the `-S` part to keep the package
default. After editing the file the first time, run
`systemctl restart haproxy`: a reload keeps the command line HAProxy was
started with, so it wouldn't pick up the new `-f`.

**Route to it from your frontend.** Add one `use_backend` line to the
frontend that terminates TLS on port 443:

```haproxy
frontend https
    bind :443 ssl crt /etc/haproxy/certs/
    use_backend %[req.hdr(host),field(1,:),lower,map(/etc/haproxy/bellhop.map)]
    default_backend my-fallback
```

`field(1,:)` drops an explicit port from the `Host` header and `lower`
matches the map's lower-cased hostnames. A hostname that isn't in the map
falls through to your own `default_backend`. If you set `proxyConfigPath`
to a different directory, the map path in this line changes with it.

**Provide the certificates.** HAProxy can't obtain certificates itself,
and Bellhop never issues or renews one. Keep the directory named by
`bind … ssl crt` populated with a tool of your own (`certbot`, `acme.sh`)
— normally a wildcard for your domain, so a new subdomain never needs a
certificate step of its own — and have it reload HAProxy after every
renewal. HAProxy expects the certificate and key together in one `.pem`
file per certificate.

**A Let's Encrypt route that needs no Cloudflare account**: point
`certbot` at a public HTTP-01 or `--standalone` challenge instead of a DNS
plugin — any CA-issued certificate works here, since HAProxy's frontend
reads whatever `.pem` file(s) the directory holds, never anything
Bellhop-specific:

```bash
certbot certonly --standalone -d example.com -d '*.example.com' \
  --cert-name example.com
cat /etc/letsencrypt/live/example.com/{fullchain,privkey}.pem \
  > /etc/haproxy/certs/example.com.pem
```

**A self-signed route** needs no CA or public reachability at all — the
same `.pem`-with-both-halves shape, generated locally:

```bash
openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout /tmp/example.com.key -out /tmp/example.com.crt \
  -subj '/CN=example.com' \
  -addext 'subjectAltName=DNS:example.com,DNS:*.example.com'
cat /tmp/example.com.crt /tmp/example.com.key \
  > /etc/haproxy/certs/example.com.pem
```

Every browser warns on an untrusted self-signed certificate unless its
root is installed on the client — the same trade-off Caddy's own
`internal` TLS mode has.

## Applying

An apply backs up both files, writes them, and validates the result
together with your main configuration:

```sh
haproxy -c -f /etc/haproxy/haproxy.cfg -f '/etc/haproxy/bellhop.cfg'
```

If validation (or any write) fails, both files are restored from their
backups — a file that didn't exist before is removed again — and the apply
fails with HAProxy's own message. Otherwise HAProxy is reloaded with
`systemctl reload haproxy`, which also picks up the new map. (The Debian
unit's reload re-validates first too, with whatever `EXTRAOPTS` names.)

That validation checks your main configuration plus the file at
`proxyConfigPath`, but the running service loads whatever `EXTRAOPTS`
names, and your frontend reads whatever `map(...)` path it names. If you
change `proxyConfigPath`, update `EXTRAOPTS` and the frontend's `map()`
path to match and restart HAProxy — otherwise applies keep succeeding while
HAProxy goes on serving the old files.

Both files are Bellhop's alone, so an apply refuses to replace an existing
file whose first line isn't the generated header above, touching nothing.
The header names HAProxy, so it differs from the one the nginx driver
writes. That matters when switching drivers: `proxyConfigPath` is shared by
every driver, so a path left over from the Caddy or nginx driver — even an
nginx file Bellhop generated — fails with that refusal rather than being
overwritten. Clear it
(`bellhop set-config proxyConfigPath --unset --apply`) or repoint it when
switching. The other driver's own files are left in place for you to
retire by hand.

## How backends are reached

Each backend forwards the way the Caddy and nginx drivers do:

- Any `X-authentik-*` header the client sent is removed first. No backend
  this driver generates is behind forward-auth, so such a header can only
  be a client posing as an Authentik-verified user.
- `Host` passes through unchanged, and `X-Forwarded-Host` carries it too.
- `X-Forwarded-For` is *set* to the connecting address, never appended to,
  so a client can't pose as a LAN address.
- `X-Forwarded-Proto` is always `https` (every request came through your
  TLS frontend) and `X-Forwarded-Port` is always `443`.
- `timeout server` and `timeout tunnel` are one day, so a quiet WebSocket
  isn't cut off by your `defaults` timeouts (the tunnel timeout covers both
  sides of an upgraded connection). A server-sent-events stream is ordinary
  HTTP, though, so its client side still ends after your frontend's
  `timeout client` (50s in Debian's default `haproxy.cfg`) of silence; if an
  app keeps an SSE stream idle for longer, raise `timeout client` in your
  own frontend or `defaults`. HAProxy passes WebSocket upgrades through and
  doesn't buffer or limit request bodies on its own.
- No health `check` on the server line: a backend has one server, so a
  failing check would only turn a slow app into a 503.

The connection to the backend follows the same TLS rule as the other
drivers:

| Entry | Server line ends with |
| --- | --- |
| `insecureBackendTls` set | `ssl verify none` |
| port 443, `insecureBackendTls` not set | `ssl verify required ca-file /etc/ssl/certs/ca-certificates.crt` |
| anything else | nothing — plain HTTP |

One difference: HAProxy checks a port-443 backend's certificate chain
against the CA bundle but not the name on it, where Caddy and nginx also
check it against the backend's IP address. In practice this rarely
matters — a publicly issued certificate almost never names an IP address,
so such a backend needs `insecureBackendTls` under every driver.

## Limits

- **No forward-auth.** HAProxy has no forward-auth Bellhop can generate,
  so this driver accepts ungated and OIDC-mode entries only. A
  forward-gated entry (an `authGroup` with `authMode` unset or `forward`)
  is refused by `sync-proxy`, and by a guest edit that would save one,
  before anything is written:

  ```text
  Entry 'web-lxc' uses forward-auth gating, but the 'haproxy' proxy driver cannot enforce it -- set its authMode to oidc or clear authGroup
  ```

  Switch the entry to OIDC mode (the app then checks the login itself —
  see [Authentik](../authentik.md)) or clear its `authGroup`. Nothing is
  ever deployed ungated in its place.
- **Bellhop's own web UI needs nothing special.** It signs users in itself
  (see [Web login](../authentik.md#web-login)), so its route is a plain
  backend with no forward-auth in front of it — no `proxyManual` entry is
  needed. Give Bellhop's entry `authMode: oidc` and its `/auth/callback`
  URL in `oidcRedirectUris`, as for any OIDC app.
- **`unauthenticatedPaths` is ignored.** It only means something on a
  forward-gated entry, which this driver never renders.
- **No status page.** HAProxy has no document root to serve one from.
  `render-status-page` fails, saying to clear `statusPagePath` or choose
  another driver, and the web UI's push-live step logs a warning when
  `statusPagePath` is set. The Settings page hides the Status page path
  field while HAProxy is selected.
- **No shared-certificate settings.** Certificates live in your frontend,
  so `proxyTlsCertificate`/`proxyTlsKey` don't apply and are hidden too.

## Assumptions

The driver assumes a distribution-packaged HAProxy on Debian or Ubuntu,
managed by systemd. Three paths and commands are fixed rather than
configurable:

- your main configuration is `/etc/haproxy/haproxy.cfg` (validation loads
  it alongside the backends file);
- the CA bundle for verifying port-443 backends is
  `/etc/ssl/certs/ca-certificates.crt`, the same one the nginx driver uses;
- HAProxy is reloaded with `systemctl reload haproxy`.
