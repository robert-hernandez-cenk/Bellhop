# Web client

The React web UI in `web-client/src/`. It is a fully separate build with no imports from `src/`, so logic the server also needs is duplicated rather than shared (for example `sortGuestsForDisplay`/`compareIp` in `web-client/src/lib/guest-display.ts` mirror `sortInventoryForFile`'s guest ordering: by `host`, then `type`, then `ip` numerically per octet with ip-less last, then `name`). Server-side rules (routes, authorization, jobs, WebSocket) live in `src/web/CLAUDE.md`. Mobile verification of any UI change is a root `CLAUDE.md` rule (desktop and <=640px in a real browser).

## Responsiveness and theming

- A single `640px` breakpoint (`index.css`) separates desktop from mobile; there is no tablet breakpoint. Below it, `Sidebar` becomes an off-canvas drawer (fixed, translated off-screen, opened by a hamburger button, closed on backdrop tap or nav-link click). Above it, it is the static 220px column, and nav links never wrap: they truncate with an ellipsis (#74).
- Every `.data-table` (Dashboard Hosts/Bridges/Storage/Guests, JobHistory Jobs) becomes a card layout below the breakpoint: `table`/`tbody`/`tr`/`td` become `display: block`, and each `<td>` carries `data-label="..."` matching its column header, shown via CSS `::before` because `<thead>` is hidden. Any new table follows this `data-label` convention, never a horizontal-scroll container. A long card value wraps (`overflow-wrap: anywhere`, right-aligned) rather than truncating; a flex row holding a user-supplied name needs `min-width: 0` plus `overflow-wrap: anywhere` on the shrinking item (see `.job-header-main`, #5).
- Theme is controlled by `ThemeContext`/`ThemeToggle` (`web-client/src/lib/theme.tsx`), not the raw `prefers-color-scheme` query: the choice (`'light' | 'dark' | 'system'`, persisted in `localStorage`, default `'system'`) is resolved to light/dark in JS and written to `document.documentElement.dataset.theme`. `index.css` keys dark overrides off `:root[data-theme='dark']`, so new themed CSS must target that selector.

### FieldHelp

The guest Advanced modal's field explanations (#34) live in `web-client/src/lib/advanced-field-help.ts`, keyed by label and pinned by a test against the modal source. They are shown via `FieldHelp` (`web-client/src/components/FieldHelp.tsx`), an ⓘ disclosure used instead of a hover-only `title`, since `title` never shows on touch. `placement` is:

- `'row'` (default, the Advanced modal): the explanation spans the form row and scrolls into view inside the modal.
- `'anchored'` (#75, the Update page's `AppUpdateBadge`): a `position: fixed` popover placed beside the marker by the pure `web-client/src/lib/popover-position.ts` (`placePopover`/`popoverMaxWidth`), sized to its text up to `min(320px, 100vw - 32px)`, clamped inside the viewport, flipped above the marker when there is no room below, re-placed on scroll/resize, never `scrollIntoView`d (the badge has no positioned ancestor, so a row-mode popover laid out against `<body>` and scrolled into view made the page jump). A fixed popover assumes no ancestor sets `transform`/`filter`, either of which would make it fixed to that ancestor instead of the viewport.

## Dashboard guest Advanced modal

- `EditableAuthGroup.tsx` is the auth-group dropdown (replaced the old "requires auth" checkbox), backed by `GET /api/auth-groups` (authenticated but deliberately not admin-gated, since a non-admin needs the rung options to raise a tier). Its edits reach the proxy via the server's combined push-live step; tier raise/lower authorization is server-side (`src/web/CLAUDE.md`).
- The modal is split into General and Access tabs (#22). General holds type/ip/host/vmid/subdomains/port/proxy/VPN/app. Access holds auth group/mode plus whichever of unauthenticated paths (forward mode) or callback URLs/mobile redirect URLs/OIDC client info (OIDC mode) apply to the entry's current mode.
- `accessFieldsFor(guest)` (`web-client/src/lib/oidc.ts`) decides which Access fields show, reading the entry's *saved* mode rather than an in-progress dropdown edit, so a field hidden by a mode switch keeps its saved value. One exception, `needsCallbackUrlsBeforeOidc`: a gated forward-mode guest with no web callback URL also gets the callback URLs field, since `oidcConfigErrors` refuses its switch to OIDC until one exists.
- `renderedAdvancedFields`/`liveHelp` in `web-client/src/lib/advanced-modal.ts` decide which rows render for the current tab and so which field-help state is still live.
- Changing `authMode`/`oidcRedirectUris`/`oidcMobileRedirectUris` (`EditableAuthMode.tsx`/`EditableOidcRedirectUris.tsx`/`EditableOidcMobileRedirectUris.tsx`) is admin-only server-side in both directions (see `src/web/CLAUDE.md`). An edit that takes an OIDC entry to anything else needs the confirmation flag described in `src/operations/CLAUDE.md`: `EditableAuthMode` shows a `ConfirmDeleteModal` naming the app before resending with `confirmOidcClientDeletion: true`, and if the server still rejects a confirmed save (a concurrent edit changed something first) it reopens the same modal rather than surfacing a raw error.
- Banners for a successful guest-PATCH's sync outcome: `AuthentikConflictBanner` (`AuthentikSyncBanners.tsx`, shared; offers the Adopt button for an admin on an OIDC-effective guest, a "switch to OIDC mode, then adopt" note for a forward-mode one, "resolve by hand" otherwise), `AuthentikSkipBanner` (renders the `oidcSkipped` list: why the sync left the guest alone), a warning banner for `oidcDiscoveryFailures` (the OIDC counterpart of the `authentikConflicts` banner), and a warning banner under the mobile redirect URL field for `mobileConsentProblems`. `EditableAuthGroup`/`EditableSubdomains` render the `authentikConflicts` warning; a mismatch between its slug and the edited guest's `subdomains[0]` fails silently by rendering nothing.
- `OidcCredentials.tsx` (the Advanced modal's reveal button) calls the admin-only credentials route directly; a non-admin sees a plain "OIDC (credentials visible to admins)" note instead of a disabled control, including under impersonation.
- `AdoptOidcClientButton` sits next to the conflict banner on `EditableAuthMode`/`EditableOidcRedirectUris` and uses `POST /api/oidc/:entry/adopt/preview`/`/apply`.
- A read-only "Created by" row on the General tab shows `creator.username` when recorded and no row otherwise; the uid is never shown.

## Provisioning forms

- Storage fields use the `select-storage` `FieldKind` with `storageContentTypes` on the field def: `install-app` Template Storage/Container Storage, `create-lxc` Storage, `create-vm` Disk Storage, and `deploy-vpn-gateway` Storage. Each populates from the selected host's `storages[]`, re-filters and re-selects a default when the host changes (same pattern as the Bridge field), and falls back to `pickStorage`'s automatic selection server-side when left unset.
- The Deploy VPN Gateway form (VPN Provider/Host/MID/Name/Storage) shows and masks per-provider credential fields (Access Token for NordVPN, Username/Password for PIA; `FieldDef.showIf`, `kind: 'secret'`). `required: true` is declarative only: nothing in `ProvisioningForm.tsx`/`FieldInput.tsx` reads it, so a blank credential is caught by the command's own check. A new form field must also be added to its operation's `shape` (`src/operations/CLAUDE.md`).
- The MID suggestion, migrate-guest's preferred-MID collision check, and the MID field's collision warning read `GET /api/provisioning/used-mids` (occupied MIDs per host the caller may see, never guest names), not the filtered `GET /api/inventory`, since the filtered list can't account for every guest (#54). The warning names a guest only if it is in the caller's visible list.
- `AppCheckInput.tsx` backs the App field: a type-to-filter suggestion popup fed by `GET /api/provisioning/install-app/apps`, grouped `ProxmoxVE (stable)` above `ProxmoxVED (development)`, with a custom-repository group (labelled `owner/repo@branch`) first when configured. The field stays free text (a full script URL still works); the catalog is only a suggestion list, and every failure path degrades to a plain text input. Only slugs are offered, with no descriptions, categories, or icons.

### Prompt banner (`promptBannerView`)

The job-prompt banner's hint text, dismiss-button label, and which controls get the quiet/outline treatment per origin all come from one `Record<PromptOrigin | 'none', ...>` table, `promptBannerView()` in `web-client/src/lib/prompt-banner.ts` (#4), so a new origin cannot ship without banner copy. Every pause carries its origin (`expected`/`heuristic`/`stall`) through the job row and WebSocket; `JobView` numbers a known prompt ("question 2 of up to 4") and flags a stall as a guess rather than a detected question. Detection itself is server-side (`src/web/jobs/CLAUDE.md`).

## Who-am-I, Sidebar, impersonation

- `GET /api/whoami` is fetched once per page load through the shared `WhoAmIProvider`/`useWhoAmI()` (`web-client/src/lib/whoami.tsx`; fetch/staleness/generation logic in `whoami-store.ts`). `Sidebar`/`UsersPage` read `isAdmin`/`adminGroups`/`capabilities` from that hook rather than fetching themselves; `GroupsSection` is a plain prop consumer, getting `adminGroups` from `UsersPage`. The admin group names have one definition (server settings); the client duplicates none.
- Starting/stopping impersonation from the Sidebar `await`s `WhoAmIProvider`'s `refresh()` rather than `window.location.reload()`; that bumps the store's `generation` and remounts the routed page so it refetches under the new identity. A failed lookup shows inline in the Sidebar with a Retry control that reloads the page instead of calling `refresh()` (the banner shows only once the identity has already failed to load, so a reload loses no in-page state).
- **Sign-in (#69)**: `api/client.ts`'s `check()` turns any 401 from `/api` into `location.href = /auth/login?returnTo=<current path>` (the login route lives under `/auth`, so it cannot loop). `Sidebar` shows **Sign out** for a real session as a plain `<form method="post" action="/auth/logout">` (a top-level navigation the provider's sign-out can redirect through; POST only so a link cannot sign anyone out), and the "no authentication configured" warning for the local operator.
- `Sidebar.tsx` decides the Admin nav group through `adminNavLinks(isAdmin, hasDirectory)` (`web-client/src/lib/admin-nav.ts`, framework-free so it is tested with plain `node --test`): `hasDirectory: false` returns Settings alone, `true` returns Users/Permissions/Settings in that order, and the "Admin" `nav-group-label` renders only when the list is non-empty. The impersonation picker's own `isAdmin && hasDirectory` gate is separate: impersonating a group is an Authentik directory operation.
- Local dev (`npm run web:dev`) sets `WEB_UI_DEV_GROUPS=bellhop-admins`; see `src/web/CLAUDE.md` (Web UI authentication) for the admin-group caveat. Symptom in the UI: if the effective admin group differs, the auth-group dropdown's `canLower` comes back `false` and widening a tier or clearing a gate is refused.

## Settings page

`/settings` (`web-client/src/pages/SettingsPage.tsx`, #124, #20, #64) is the editor for the settings store; the server side is `GET`/`PATCH /api/settings` (`src/web/routes/settings.ts`, see `src/web/CLAUDE.md`). Framework-free helpers live in `web-client/src/lib/settings-display.ts`, tested with plain `node --test`.

- **Tabs**: `SETTINGS_TABS`/`fieldsForTab` split the page by integration: General, Proxy, Authentik, Cloudflare, GitHub. #73 removed the Nginx Proxy Manager tab; its three fields (`npmApiUrl`/`npmApiEmail`/`npmApiPassword`) sit at the end of the Proxy tab.
- **Drivers dropdown**: `proxyDriver` renders as a `<select>`. `proxyDriverOptions(drivers, defaultId)` builds options from the response's `proxyDrivers`/`defaultProxyDriver`, suffixing only the default driver's label with `" (default)"`. The displayed value is `drafts.proxyDriver || data.defaultProxyDriver`, so an unset setting shows the default selected, and Save/Clear round-trip like any field. Until the driver list has loaded (or if the load fails) the dropdown is a disabled, option-less `<select>` with Save disabled, never free text.
- **Caddy TLS dropdown** (#51): a second `<select>`; `caddyTlsOptions(modes, defaultMode)` builds it from `caddyTlsModes`/`defaultCaddyTls`, labelling only the default `cloudflare (default)`. Shown only while the selected driver's `usesCaddyTls` is true (`showCaddyTlsField`); displayed value `drafts.proxyCaddyTls || data.defaultCaddyTls`; disabled with Save disabled until the driver list loads.
- **`proxyFieldView(selectedId, drivers, caddyTls)`** decides, for the driver selected in the *unsaved* dropdown, which fields apply:
  - A driver whose `managesProxy` is `false` (`none`) hides Proxy config path, Status page path, Caddy TLS, Proxy TLS certificate/key, cert resolver, API URL and the NPM fields entirely.
  - A managed driver with a `defaultConfigPath` shows Proxy config path with that path as placeholder, appending the driver's `configPathNote` to the help text when it has one. A driver with `defaultConfigPath: null` (Nginx Proxy Manager, Caddy admin API) hides it, since there is no file to name.
  - Status page path shows only when `suggestedStatusPagePath` is non-null (`null` for Nginx Proxy Manager, HAProxy, Traefik; the Caddy admin-API driver has no file but suggests one, so it shows Status page path alone). `statusPagePath`'s help text is static; only its placeholder is driver-driven.
  - The two TLS fields (Proxy TLS certificate/key) show when `usesSharedCertificate` is true (nginx) or `usesCaddyTls` is true *and* the Caddy TLS dropdown's value is `files` (`showTlsFields`).
  - Proxy cert resolver / Proxy API URL show only when `usesCertResolver`/`usesApiUrl` are true (`showCertResolverField`/`showApiUrlField`; Traefik only).
  - The NPM fields show only when `usesNpmApi` is true (`showNpmApiFields`).
  - All metadata-driven, never an id comparison in the page. An unrecognized id (unreachable through the dropdown) hides all of them. The TLS, cert-resolver/API-URL and NPM fields also stay hidden until the driver list has loaded, since they mean nothing for the default driver.
  - Hiding is display-only: a draft and its stored value are never touched, and no PATCH is sent because a field stopped being shown (NPM fields included: switching away and back never clears or resends their drafts), so switching back to a driver that uses it shows the old value.
- **Derived values** (read-only, from `derivedValues()` on the server): each host's `midScheme.gateway`, with an explained empty state (`LAN_GATEWAYS_EMPTY_TEXT`).
- **Environment-pinned and secret fields**: the response's `sources` (every non-secret key's `environment`/`settings`/`none`), `environment` (only keys an env var currently pins: `{ variable, value?, stored, storedValue? }`, `value` never present for a secret) and `secrets` (`{ set, source }`) drive rendering. `settings` holds only *stored* non-secret values, which is what the inputs edit. A pinned field renders read-only, labelled "set by environment" with no Save/Clear and a "Stored copy" line (how an operator confirms an import before deleting a `data/*.env` file). A secret renders as a masked, never-pre-filled input with Replace/Clear and a status line (`secretStatusText`), cleared after every save.
- **`confirmationMessage`**: the page confirms before saving either admin-group field or leaving `webUiAuthMode: oidc`.
- The Settings nav link shows for any admin even without Authentik's user directory (it needs only an identity); non-admins and impersonating admins get 403 from the API.
